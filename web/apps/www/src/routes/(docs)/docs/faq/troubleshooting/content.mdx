The first place to search when something is on fire. Each recipe
is a single symptom, a likely cause, and a fix. The list is not
exhaustive — it is the top 12 things that operators hit.

## Workload is stuck in `Pending`

**Symptom.** A workload you just created does not move out of
`Pending`. The detail view's state chip stays orange.

**Likely cause.** The assigned node agent has not picked up the
workload. Either the agent is offline, or the workload's command
queue is backed up behind a stuck workload from earlier.

**Fix.** Open the workload's detail view and check the
`LastReportedAt` timestamp. If it is more than a minute in the
past while the workload is in `Pending`, the agent has not
checked in. Restart the workload to re-queue the command; if
the restart does not move it forward, restart the NodeAgent.

## Workload is stuck in `Provisioning`

**Symptom.** A workload moves from `Pending` to `Provisioning`
but never to `Running`. The detail view's `LastMessage` carries a
runtime-specific error.

**Likely cause.** The runtime failed to allocate the resource —
typically because the disk image is missing, the network bridge is
not configured, or the host's storage backend is full.

**Fix.** Open the workload's detail view and read `LastMessage`.
The error string is the runtime's own output. Common fixes: pull
or upload the missing image, free disk space on the storage
backend, or repair the network bridge on the assigned node.

## Floating IP is assigned but unreachable

**Symptom.** A floating IP shows `Assigned` but `ping` or
`curl` from outside times out.

**Likely cause.** The assigned workload is not running, or the
VPC's network path is broken.

**Fix.** Confirm the assigned workload is in `Running`. If yes,
check the workload's port bindings — the listener might be on a
different port than the test traffic is targeting. If the
workload is in `Stopped`, start it; the floating IP routes
within seconds.

## Load balancer is `Degraded`

**Symptom.** A load balancer shows the orange `Degraded` chip.
Some targets are reachable, some are not.

**Likely cause.** At least one target workload is in `Stopped`,
`Failed`, or `Pending`.

**Fix.** Open the load balancer's detail view, click into the
target list, and identify the unhealthy target. The probe
refreshes every 30 seconds; after the target returns to
`Running`, the load balancer moves back to `Active`.

## API requests return 429

**Symptom.** `POST` and `PUT` requests return HTTP 429 with
`code = "quotas.exceeded"`.

**Likely cause.** A quota walker returned Denied for the
request's scope and key.

**Fix.** Read the response's `extensions.limit`, `extensions.used`,
and `extensions.requested`. The fix is one of: delete unneeded
resources, raise the quota at the appropriate scope, or move
the resource to a folder with capacity. There is no admin
override path.

## Login returns HTTP 423

**Symptom.** Login attempts return 423 with
`code = "identity.credentials.locked"`.

**Likely cause.** The user account is in a lockout window after
5, 10, or 15 consecutive failed logins.

**Fix.** Wait the window out (15 minutes, 1 hour, or 24 hours)
or have an admin reset the password from the **Users** page.
The lockout resets on a successful login.

## A user cannot see a folder

**Symptom.** A user has role bindings but the folder selector
does not list a folder the user expects to see.

**Likely cause.** The role binding's scope is narrower than the
folder. A folder-scoped binding does not grant visibility to a
sibling folder.

**Fix.** Open the user's role bindings and confirm the scope of
each binding matches the folder. If the user needs visibility
across all folders in the team, scope the binding to the team.
If the user needs visibility across the whole org, scope the
binding to the org.

## Theme does not activate

**Symptom.** The marketplace shows a theme as installed, but
clicking **Activate** has no visible effect.

**Likely cause.** The theme's CSS variables collide with the
brand's. The theme is applied, but the resulting look is
indistinguishable from the brand.

**Fix.** Open **Admin → Branding** and reset the accent colour
and surface tint, then re-activate the theme. The theme's
variables now take effect on top of the brand's neutral
defaults.

## Audit log returns 401

**Symptom.** `GET /api/v1/audit` returns HTTP 401.

**Likely cause.** The bearer token has expired or the JWT is
older than 15 minutes.

**Fix.** Refresh the token (call the refresh endpoint with the
refresh token) or sign in again. If the bearer is a long-lived
API key, confirm the key has not been revoked.

## Volume resize failed

**Symptom.** A volume's resize action reports
`storage.volumes.resize` failed.

**Likely cause.** The storage backend is out of capacity, or the
new size is not larger than the current size.

**Fix.** Open the storage backend's detail view and confirm
capacity. Confirm the new size is larger than the current size
(shrinking is not supported). If both checks pass, check the
audit log for the storage-backend-specific error message.

## Brand changes do not persist

**Symptom.** Edit the brand fields, click **Save**, reload — the
brand is back to the old values.

**Likely cause.** Two operators are editing the brand
simultaneously; the second save wins, and the first operator's
view does not refresh.

**Fix.** Reload the page; the latest saved values appear. To
prevent the race, coordinate brand edits in chat — there is no
lock UI in the current release.

## Backups fail silently

**Symptom.** A scheduled `pg_dump` task runs at the configured
cadence but the destination bucket is empty.

**Likely cause.** The dump task lost its credentials, the bucket
policy denies the dump task's principal, or the dump itself is
failing on the source database.

**Fix.** Run the dump task by hand with verbose output. The
error stream will name the failing step (authentication, network,
or query). For a query failure, run `pg_dump` directly against
the database; the error message from Postgres is the source of
truth.
