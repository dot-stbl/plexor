Networking in Plexor is a small, predictable set of primitives:
virtual networks (VPCs) that isolate workloads from each other,
floating IPs that move between nodes, and load balancers that
distribute inbound traffic across multiple workloads.

## VPCs and subnets

A VPC (Virtual Private Cloud) is a Layer 2 broadcast domain inside
your Plexor host. Workloads attached to a VPC can talk to each
other; workloads in different VPCs cannot, unless you add a peering
link.

Inside a VPC you define one or more subnets. Subnets are the unit
the workloads themselves bind to — a workload's network interface
lives on exactly one subnet, and that subnet determines the
workload's IP address.

Subnet sizing follows the conventional rules:

- Reserve the first address for the gateway.
- Reserve the last address for broadcast (legacy; ignored by modern
  stacks but kept for symmetry with operator muscle memory).
- Leave a few addresses free for future services.

Plexor does not impose a particular subnet layout. The default is
`10.0.0.0/16` with `/24` subnets, which is enough for most home-lab
deployments; you can pick any RFC 1918 range you want, as long as it
does not collide with the host's primary network or any VPC you
already have.

## Floating IPs

A floating IP is a public IP address that you reserve and then
attach to a workload. The floating IP is the thing the outside world
talks to; the workload's private IP stays internal to the VPC.

Two operators use floating IPs for two different jobs:

- **Inbound traffic** — reserve a floating IP, point a DNS record
  at it, attach it to a workload that runs a public-facing service
  (a web server, a VPN endpoint, a Minecraft server).
- **Workload migration** — attach the floating IP to one workload,
  then re-attach it to another to move the public address without
  waiting for DNS propagation. The re-attach is a single API call;
  the floating IP moves in seconds.

A floating IP belongs to an organisation, not to a workload. You
reserve it, you assign it to a workload, and when the workload is
deleted the floating IP remains reserved (and billable against the
quota) until you release it.

## Load balancers

A load balancer sits in front of a list of workloads and distributes
inbound traffic across them. Plexor supports two algorithms in the
current release:

- **Round-robin** — distribute requests across the target list in
  order, one per request, looping. Good default; no per-target
  accounting.
- **Least-connections** — distribute to the target with the fewest
  open connections. Better fit for workloads with sticky
  connections (long polls, WebSockets).

A load balancer has a state: `Active` when the platform can reach
every target, `Degraded` when some targets are reachable, `Inactive`
when no targets are reachable. The state is computed at probe time
(every 30 seconds in the current release) and surfaces in the load
balancer's detail view.

Adding or removing a target from the load balancer takes effect at
the next probe. Existing connections to other targets are not
interrupted.

## What ships today vs. what comes later

The current release ships VPCs, subnets, floating IPs, and load
balancers. Security groups are on the roadmap — the navigation in
the console shows the route, but the page links to a "Soon" entry
because the feature is not yet wired to the data plane.

| Capability | Status |
|---|---|
| VPCs and subnets | Shipped |
| Floating IPs | Shipped |
| Load balancers | Shipped |
| Security groups | Soon |
| DNS as a service | Soon |
| Cross-host networking | Soon (multi-host clustering) |

The "Soon" entries are not abandoned features; they are tracked
specs whose implementations have not yet landed. When each ships,
the relevant concept page picks it up.

## What the operator sees when something is wrong

Three things break most often in practice:

1. **A workload cannot reach the internet.** The most common cause
   is a missing route from the VPC subnet to the gateway. Open the
   VPC detail view, check the subnet's gateway, and confirm the
   subnet's CIDR is routable.
2. **A floating IP does not respond.** The floating IP is
   assigned to a workload that is no longer running, or the
   workload's security policy is dropping inbound traffic. Open
   the floating IP's detail view, confirm the assigned workload is
   in `Running`, and check the workload's port bindings.
3. **A load balancer shows `Degraded`.** One of the targets is
   unreachable. Open the load balancer, click into the target
   list, and identify the unreachable workload — typically a
   workload that was recently restarted and has not yet been
   probed as healthy.
