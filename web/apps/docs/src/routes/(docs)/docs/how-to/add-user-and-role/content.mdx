A Plexor user is anyone who authenticates against the platform —
an operator, an end-user of a hosted app, a service account. This
page walks through adding a user and granting them the permissions
they need.

## Step 1 — Open the users page

From the sidebar, choose **Access → Users**. The page shows every
user in the current organisation, their role bindings, and their
last login.

## Step 2 — Invite the user

Click **Invite user**. The dialog asks for:

- **Email** — the user's email address. Plexor stores the address
  lowercased; case does not matter.
- **Display name** — the human label that shows up in the audit log
  and the top-right avatar.
- **Initial role** — the role the user gets on first login. You
  can pick a built-in role or a custom role; the role binding scope
  determines where the role's permissions apply.

Click **Invite**. Plexor sends an email invitation; the user
clicks the link, sets a password, and lands in the console.

<Callout type="info">

If the organisation is configured for OIDC, the **Invite user**
dialog skips the email flow — Plexor tells you the user has been
"linked to the IdP" and the user signs in through the external
identity provider. See **Configure OIDC**.

</Callout>

## Step 3 — Adjust the role bindings

A user's effective permissions are the union of every bound role's
permissions. To grant a user access to a specific folder, open the
user's detail view and click **Add role binding**.

The form asks for:

- **Role** — the role to bind. Plexor ships four built-in roles
  (`admin`, `operator`, `viewer`, plus the implicit `*` super-admin)
  and any custom roles the org has created.
- **Scope** — `Org`, `Team`, or `Folder`. Pick the narrowest scope
  that satisfies what the user needs to do.

A common pattern:

- `viewer` on `org` — every user can see everything that exists.
- `operator` on `folder` — the user can run workloads in their
  folder but cannot edit quotas or org-wide settings.
- `admin` on `folder` — the user owns their folder's lifecycle.

The same user can hold all three. The bindings stack.

## Step 4 — Verify

Sign in as the new user (in a private browsing window) and confirm
the scope switcher shows the right scope and the role's permissions
are in effect. The audit log carries every binding change with
`action = identity.role.binding.changed`; if the audit trail
matters for compliance, that is where you find it.

## Revoking access

Three ways to revoke a user's access, in order of severity:

1. **Remove the role binding** — the user keeps the account but
   loses permissions. The change is instant for any subsequent
   request; existing JWTs keep their snapshotted permissions until
   they expire (15 minutes) or the user refreshes.
2. **Suspend the user** — the user cannot authenticate. Useful
   for an employee on leave.
3. **Delete the user** — the row is removed. The audit log
   preserves a record of the user's actions; the user cannot sign
   in again.

Plexor does not soft-delete users. If you need to preserve the
audit trail but prevent further access, suspend rather than delete.

## What to do next

- **Issue an API key** for the user if they need to run scripts
  against the REST API.
- **Configure OIDC** if you want to stop managing passwords
  manually.
