API keys are long-lived service credentials. Plexor's own NodeAgent
authenticates with an API key; so do any scripts you write against
the REST API. This page walks through issuing one.

<Callout type="warning">

The raw API key secret is shown **exactly once** in the create
dialog. After the dialog closes, Plexor stores only the SHA-256
hash of the secret; you cannot retrieve it. Copy it to a password
manager before you close the dialog.

</Callout>

## Step 1 — Open the API keys page

From the sidebar, choose **Access → API keys**.

The page shows every API key in the current organisation: who owns
it, which permissions it has, when it last authenticated, and
whether it is still active.

## Step 2 — Issue the key

Click **Issue API key**. The dialog asks for:

- **Name** — what the key is for (`nodeagent-prod-host-1`,
  `backup-runner`, `metric-exporter`).
- **Owner** — the user the key belongs to. The owner must already
  exist in the organisation. Plexor refuses to issue a key
  against a user with no role bindings.
- **Permissions** — the permission set. The set must be a subset
  of the owner's effective permissions; Plexor returns 403 if you
  try to grant a permission the owner does not hold.

Click **Create**. Plexor shows the raw secret exactly once.

The bearer format is:

```
Bearer kid_<key_id>.<secret>
```

`<key_id>` is the key's UUID v7 (prefixed `kid_`), `<secret>` is
a 43-character base64url string.

## Step 3 — Store the secret

Use a password manager or a secrets manager. The Plexor admin guide
includes a recipe for storing Plexor API keys in HashiCorp Vault;
the NodeAgent itself reads the secret from a file on disk that the
installer sets to mode 0600.

A leaked key is not recoverable. If the secret lands in a chat
transcript, an email, or a code repository, treat it as
compromised — rotate the key, do not just delete the old one.

## Step 4 — Use the key

For a NodeAgent, the secret is read from a file at startup. The
NodeAgent's startup config takes the bearer token verbatim:

```
Authorization = "Bearer kid_0192c8e3-...<your key id>...<your secret>"
```

For a script, the bearer is set on the HTTP client:

```bash
curl -sS \
  -H "Authorization: Bearer kid_<key-id>.<secret>" \
  https://plexor.example.com/api/v1/workloads
```

A successful request returns 200. A 401 means the bearer is wrong
(case-sensitive, no extra whitespace). A 403 means the key lacks
the required permission — re-check the issue dialog.

## Step 5 — Revoke or rotate

When the key is no longer needed, or you suspect it has leaked,
open the key's detail view and click **Revoke**. Plexor sets the
key's `RevokedAt` to the present moment and refuses to authenticate
against it. Revoke is irreversible from the API side — to restore
access you issue a new key.

To rotate an active key without downtime:

1. Issue a new key with the same name suffix (`-v2`).
2. Update every consumer to use the new bearer.
3. Revoke the old key once you have observed the new key in use.

The audit log carries both events.

## What to do next

- **Rotate API keys** on a regular cadence — the recipe in the
  admin guide covers the schedule.
- **Inspect the audit log** if you want to see when each key last
  authenticated and from which client.
