RBAC in Plexor is a flat permission catalog. There are no
wildcards (the `*` super-admin role is the single exception) and
no inheritance — every permission string is a literal grant or
denial. This page covers the security implications of that model
and the patterns that make a Plexor deployment safe.

<Callout type="warning">

The 15-minute JWT snapshot window is the most often-missed
security boundary in Plexor. If you remove a permission from a
user's role, the user's existing JWT still carries that
permission until the token expires or is refreshed. Plan
permission changes with this window in mind.

</Callout>

## Why no wildcards

A wildcard permission like `compute.vms.*` reads as "everything
VM-related". It is convenient to write and brittle to evolve: if
Plexor adds `compute.vms.snapshot` next quarter, every role that
granted `compute.vms.*` silently gains the new permission.

The flat-permission model forces the grant to be explicit. A role
that lists `compute.vms.create`, `compute.vms.delete`, and
`compute.vms.read` does **not** gain `compute.vms.snapshot` when
it ships. Adding the new permission requires an explicit edit to
the role, an audit entry, and a JWT refresh for the change to
take effect.

The single exception is `*`, which marks the super-admin role.
A user with a role binding that includes `*` short-circuits every
permission check, including permissions that have not yet been
invented. The seed admin always carries `*`; treat it as
break-glass and do not bind `*` to anything else.

## Writing a least-privilege role

A NodeAgent integration is the most common case for a
least-privilege role. The agent authenticates with an API key
issued against a service user; that user's role bindings
determine the agent's effective permissions.

The pattern:

1. Create a service user `nodeagent-prod` (no email, no display
   name — just an identity for the agent).
2. Create a custom role `nodeagent-runtime` with the **minimum**
   permission set the agent needs:

   - `compute.workloads.read` — to enumerate workloads.
   - `compute.workloads.create` — to start workloads on its node.
   - `compute.workloads.delete` — to clean up workloads that
     fail.
   - `compute.nodes.heartbeat` — to send periodic heartbeats.

3. Bind the role to the user at the folder scope (or the team
   scope if multiple folders share an agent).

4. Issue an API key against the user with the same permission
   subset.

The Plexor refuses to issue an API key with permissions the owner
does not hold (HTTP 403, code `identity.permission.denied`). If
you add a permission to the role, the existing key still lacks it
until the key is rotated; rotating re-evaluates the permission
subset against the owner's current set.

<Callout type="warning">

A NodeAgent with `*` is a NodeAgent that owns the host. Do not
bind `*` to a service user. The seed admin's `*` is intentional;
a service user's `*` is a privilege-escalation path waiting to
happen.

</Callout>

## The 15-minute window

JWTs are issued at login with a 15-minute lifetime. The
`roles[]` and `permissions[]` claims are snapshots of the user's
effective permissions at sign time. Permission changes — adds,
removes, role-binding edits — do **not** take effect on an
already-issued token until the token expires or the user
refreshes.

Two operational implications:

1. **Permission changes are not instant.** Removing a user from
   the `admin` role today does not strip admin from the user's
   current session until at most 15 minutes from now. The audit
   log records the role-binding change; it does not invalidate
   existing sessions.
2. **Forced logout requires an explicit step.** To immediately
   strip permissions, revoke the user's refresh token (forces
   re-login) or suspend the user (forces re-authentication at
   next request).

The 15-minute window is the platform's tolerance for in-flight
requests during an incident. A shorter window would force more
re-logins during normal operation; a longer window would let
stolen tokens stay useful for longer after detection. The
balance is the typical session-refresh cadence for a working
operator.

## Fail-closed by default

Plexor does not have implicit grants. A user with no role
bindings has no permissions; a permission that exists in the
catalog but is not in any of the user's roles is denied; a
binding without a role is rejected at save time.

The `[RequirePermission]` attribute is fail-closed: missing
authentication returns 401, missing permission returns 403. There
is no `allow if missing` flag and no negative-permission syntax.
The only way to grant a permission is to put the literal string
on a role that is bound to the user.

## What the operator sees when something is wrong

| Symptom | Likely cause | Fix |
|---|---|---|
| A user logs out and back in and still has a removed permission | The audit entry is missing or the role still includes the permission | Confirm the role's `Permissions` list no longer contains the permission. |
| An API-key request returns 403 even though the owner has the permission | The key was issued before the permission was added | Rotate the key. The new key picks up the owner's current permissions. |
| A user with the admin role cannot edit org-wide settings | The role binding scope is wrong (folder-scoped instead of org-scoped) | Edit the binding to widen the scope. |
